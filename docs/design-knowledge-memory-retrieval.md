## 0. 目标与边界

一句话：**一个全局知识库、每个工作区一份记忆，共用一个「分块 + 全文 + 向量」的检索内核；引擎管真相与校验，
宿主只提供它算不了的东西（系统向量、可选分词），检索永远返回带来源的证据，不在核心里生成答案。**

- 取 RAG 的检索侧能力：分块、向量、混合检索、融合排序、可选的查询改写。
- 不取 RAG 的生成侧：核心不调模型、不拼答案、不做「LLM 自动抽取记忆当作真相」。记忆是显式笔记，知识是带来源的页面。
- 不做：桌面应用、内置向量模型、跨语言语义互查（中文查询命中英文原文只能靠文中本来出现的对应词）。
- 情感系统是独立的，本次不改；本方案只给它留接口（§5.4），后续由它来适配新记忆与新知识。

## 2. 调研：别的引擎怎么做（按调研顺序）

**Meilisearch（你点名的那一个）**
- 许可证是拼起来的：核心 MIT，「企业版」目录 BUSL-1.1（非生产可用，四年后转 MIT），LMDB 连接器 heed 另加 OpenLDAP 条款。来源：仓库 `LICENSE`。
- 搜索引擎核心 `milli` 是 `publish = false`（从没发布到 crates.io），依赖 LMDB、rayon、外排、地理索引，甚至自带 HTTP 客户端。想「只用它的核心」等于把整个搜索引擎连同 LMDB 搬进来。来源：`crates/milli/Cargo.toml`。
- 真正能单独用的是它的**分词核心 `charabia`**：MIT，crates.io 0.10.0 正常发布，中文 = jieba（`jieba-rs`，MIT），
  拉丁文做 CamelCase 切分 + Unicode 归一化；官方性能表：中文分词约 10 MiB/s、完整分词约 5 MiB/s。来源：charabia README / crates.io。
- 结论：**整体太重（官方二进制 333 MiB），不引入；分词思路与 jieba 词表可用。**

**向量加全文的融合（各家参数与陷阱）**
- Qdrant：RRF 与 DBSF；RRF 常数 `k` 可配（示例 60，接口默认 2），权重默认 1；预取可同时查稠密与稀疏；文档明确警告「不先归一化就做加权分数融合不可靠」。
- Weaviate：BM25F + 向量，`alpha` 0 到 1（1 = 纯向量），v1.24 起默认「相对分数融合」。
- Elasticsearch：RRF 参数 `rank_constant` 默认 60，至少两个子检索器，示例即 BM25 + kNN；RRF 用名次不用原始分数。
- LlamaIndex：`QueryFusionRetriever([vector, BM25], mode="reciprocal_rerank", num_queries=4)`，会**用 LLM 生成 3 条查询变体**（设为 1 可关）。我们只借融合，不借「默认让 LLM 改写查询」。

**记忆系统（隔离做法）**
- mem0：检索时按 `filters={"user_id": …}` 过滤，写入 `memory.add(messages, user_id=…)`——隔离靠过滤，是**逻辑隔离**。
- Zep/Graphiti：`group_id` 划分图谱，「语义 + BM25 + 图遍历」混合检索；README 自己警告服务端不鉴权，任何调用方都能读写任意 `group_id`。
  **教训：隔离必须写在引擎代码里按目录/集合强制，不能只靠调用方自觉。**

**分块与上下文**
- RAGFlow：按文档类型用模板分块，分块可视化、可人工干预（README 已核实）。
- 通用教训：先切块再检索、块与页双向可追溯、页面变了只重做这一页——与本项目「来源撤销必须使相关内容失效」天然一致。

## 3. 目标架构

### 3.1 数据布局（无软链接，项目目录不写任何东西）

```text
~/.memorycorridor/                       引擎打开的唯一真实目录（默认；--vault 可指向别处）
├── index.mbt.md  purpose.md             知识目录声明与意图
├── raw/<仓库名>/…                       全局知识库：来源文件（导入副本）
├── wiki/                                全局知识库：知识页面
├── state/
│   ├── memory/<工作区ID>/<笔记ID>.json   记忆笔记（权威）
│   ├── workspaces/<工作区ID>.json        工作区登记（引擎登记在账本里）
│   └── orders/ events/ …                工单、事件、恢复日志（必须保留）
├── index/                               索引总目录（生成的导出，可重建）
│   ├── projects.json                    规范路径 → 工作区 ID/名称
│   ├── memory/<工作区ID>/…               项目级笔记的可读导出（给全局助理）
│   └── sessions/<工作区ID>.json          会话清单与计数
├── search/                              检索产物（派生，可重建，永不是权威）
│   ├── knowledge/{chunks.json, bm25.json, vectors-<空间>.f32}
│   └── memory/<工作区ID>/…               同一套结构，按工作区隔离
├── vectors/                             页级向量（旧协议，兼容保留，标注 legacy）
└── bin/                                 辅助程序与数据（系统向量小工具等）
```

- 工作区 ID = `<目录名>-<sha256(规范路径)前8位>`；同一项目经不同路径进入仍是同一个 ID。
- 全局助理（Siri、小U同学、OpenClaw 类）：读 `index/projects.json` 找到项目，再读 `index/memory/<工作区ID>/` 下的 Markdown。
  这些是普通文件、只读语义，引擎账本不登记它们，外部改动不会触发 `content_changed`。
- 物理上「知识库与引擎分开」做不到：引擎只打开一个目录且拒绝路径上任何软链接（`platform/fs.c` 实测）。这里的分法是
  **程序与数据分家**：引擎程序在仓库/发行包里，知识库与记忆都在 home。要真正分成两个目录，只能改软链接加固层，不建议。

### 3.2 权威与派生（本方案的核心不变量）

- **权威**：`raw/`、`wiki/`、`state/memory/`、`state/workspaces/`、`state/orders|events/…`。
- **派生**：`search/` 下的块表、BM25、向量矩阵，`index/` 下的助理导出。删除任意派生数据，都能从权威重建；
  来源撤销/页面重建时，引擎在同一操作里同步删掉对应块并重建受影响集合，绝不出现「来源已失效、检索还能命中」。
- 检索永不返回派生数据里的原文之外的东西；命中必须能回到页面/笔记 ID 与来源路径。

## 4. 检索：分块 + 全文 + 向量，一个内核两个集合

### 4.1 一个内核

知识库集合 `knowledge`（全局一个）与记忆集合 `memory/<工作区ID>`（每个工作区一个）**用同一套分块、索引、检索、融合代码**，
只是索引实例不同。隔离靠「不同集合、不同文件」强制，不靠查询时过滤——跨工作区查到别人的笔记在结构上不可能。

### 4.2 分块

- 按段落切，相邻段合并到约 800 字符，块间重叠约 80 字符，超长段按句末标点再切、最后硬切（参数先用 MoonRetrieve 默认值，可调）。
- 块 ID = `<页面ID>#<序号>`；块表记录页面 ID、块序号、块的文本哈希、字符区间。块只存引用关系与哈希，**不复制正文**。
- 页面内容哈希不变 → 块表与向量全部复用；变了 → 只重做这一页的块。

### 4.3 双路检索

| 路 | 实现 | 何时用 | 已知优劣 |
|---|---|---|---|
| 全文 | BM25 倒排（MoonRetrieve `SearchIndex`），中文单字+双字内置；可选 jieba 词级分词；短语/布尔/前缀查询可单独用 | 永远开启 | 精确、可解释、能定位唯一标识符；中文靠 n-gram 兜底召回 |
| 向量（系统层） | macOS `NLEmbedding` 句向量（中文 640 维、英文 512 维），宿主小工具算，引擎存取 | 有系统向量且查询是单一语种 | **实测不比词面检索强**（§7.1），只当补充；中英不能互查 |
| 向量（算法层） | 字符 2–3 元组 + 词单元的哈希特征向量（256–512 维，L2 归一化），引擎内纯算法计算 | 没有系统向量、或查询混合语种 | 不分语种、永远可用；不做语义互译；就是「暴力算法兜底」 |

- 向量检索是**精确扫描**（余弦穷举）。实测：10 万 × 512 维平铺扫描 18 ms/次；本项目目标规模（见 §9）远低于此，不需要 HNSW。
- 融合：RRF（`1/(k+名次)`，k 取 60，权重默认 1:1），只融合实际开启的路；响应里写明哪几路开了、为什么（**降级不静默**）。
- 结果粒度：命中的是块，返回前归并到页面/笔记（每页取最高分块），摘录取命中块原文，附带页面 ID、来源路径、
  各路名次与向量层级。可选 `namespace` 过滤（`raw/<仓库名>/`），让当前项目内容在全局库里优先。
- 旧的页级 `search` 改为同一内核上的**页面视图**（同样的响应形状，分数会变，e2e 同步更新）；不再维护第二套搜索。

### 4.4 明确不做

- 不在核心里生成答案或摘要；不默认用 LLM 改写查询；不引入交叉编码器重排（要模型，留给外部调用方）。
- 不做跨语言语义检索的承诺；不做 ANN 索引（规模不到）。

## 5. 记忆、梦境 RSI、给情感留的接口

### 5.1 记忆：按工作区存、按会话可见

- 协议：记忆操作必须带 `workspace`（工作区 ID），可带 `session`（会话 ID）；`scope` 取 `project` 或 `session`。
  **不做旧版兼容**：`scope="workspace"`、顶层 `state/memory/<笔记ID>.json` 与「不带工作区就按旧行为读」一并移除，测试与文档同步。
- 存储：`state/memory/<工作区ID>/<笔记ID>.json`。笔记身份仍绑定 kind/scope/text/conditions/sources；工作区由目录决定。
- 可见性：读只返回本工作区的项目级笔记，带会话才加上该会话的；**别的工作区/会话的笔记等同于不存在**（不泄露存在性）。
- 工作区登记：`workspace-open {path}` 规范化路径 → 幂等登记到 `state/workspaces/`，并刷新 `index/projects.json`。
- 导出：项目级笔记导出为 `index/memory/<工作区ID>/<笔记ID>.md`（前置信息 + 正文 + 来源）；会话级笔记只计数、不导出内容。

### 5.2 记忆也用同一个搜索引擎

- `memory/<工作区ID>` 集合：笔记按同一分块规则（短笔记就是一块），同样的 BM25 + 向量 + RRF。
- `memory-search`、`memory-prefetch` 从「关键词倒排」升级到同一内核；`scope` 过滤在集合内部完成。

### 5.3 梦境 RSI 归记忆

- 梦境（`agent/dream.mbt`）与 RSI 应用器只作用于记忆集合与记忆策略，不作用于知识库。
- 知识库侧保留的是质量审计/巡检（lint、quality-audit），没有「自我改进」语义。

### 5.4 给情感系统留的接口（本次不实现）

1. 记忆读写都接受 `workspace`/`session`，情感侧按当前工作区取「记忆线索」，符合「情感跟随记忆、但状态全局一份」。
2. 事件可带 `workspace` 字段，情感事件可追溯到工作区。
3. `retrieve` 按集合取数，情感/人格层可以只读地查记忆或知识，不改变隔离边界。
4. 情感的全局状态（`evo/`）不因本次改动迁移；适配由情感模块自己在其排期里做。

## 6. 知识库初始化（把已写好的初始化器接到全局库）

`scripts/knowledge_init.py`（已写好、端到端已通过，未提交）就是唯一入口：

- 默认 `--vault ~/.memorycorridor`，`--namespace <仓库目录名>`，导入 `raw/<namespace>/…`。
- 过滤：默认排除 `node_modules`、`_build`、`target`、`.git` 等目录，二进制与超大文件跳过，Office 文档可走抽取；
- 每个文件一张工单（引擎同一时刻只允许一张活动工单），提交后建一个携带文件全文的 `source-summary` 页面；
- 重跑增量（内容哈希不变就不动），`--prune` 撤销消失文件（撤销是粘性的），`--dry-run` 不写任何东西；
- 提交完成后触发该 namespace 的增量分块与索引；多项目同时初始化用 home 级文件锁串行。
- 这一步只做内容；记忆模块完全不参与（已用 e2e 固定）。

## 7. 实测与规模问题（先修这个，全局知识库才成立）

### 7.1 准确率：现在的全文检索定位不了唯一标识符

120 页、每页 32 KiB 的知识库里，查只存在于第 77 页的 `tok-p77-9`：

| 查询 | 第一名 | 第 77 页 |
|---|---|---|
| `tok-p77-9` | 别的页面，3.0 分 | **第二，2.9 分** |
| `tok-p77-9 tok-p31-4` | 无关页面 3.9 分 | 第三（3.8）、第四（3.8） |

原因是分词把它拆成到处都有的 `tok`、`p77`、`9`，又没有「少见的词更重要」的权重。BM25（IDF + 长度归一化）+ 短语查询可解。

### 7.2 速度：几乎每个操作的开销跟「目录里有多少文件」成正比

同一台机器实测（发布版二进制，短连接长为常驻进程）：

| 规模 | 每张工单（5 个操作） | 检索 | rebuild | lint |
|---|---|---|---|---|
| 120 页 × 1 KiB（0.22 MiB） | 0.66 s | 0.10–0.13 s | 0.09 s | — |
| 120 页 × 32 KiB（3.83 MiB） | 1.13 s | 0.73–0.79 s | 0.46 s | — |
| 600 页 × 1 KiB（0.64 MiB） | 4.59 s | 0.50 s | 0.47 s | 3.77 s |

- 每张工单耗时随页数增长：50 页 0.31 s → 100 页 0.56 s → 300 页 1.79 s → 600 页 4.59 s（越来越快于线性）。
  外推：5000 页约 30 s/工单；导入 1000 个文件要 45 分钟以上。
- 采样定位（600 页）：每个请求「读取并重算全目录哈希」约 31%，入口处其他巡检约 60%，检索缓存只占约 5%；
  lint 的 3.8 s 里 82% 花在变两两比较的 `index.tokens`（平方级）。
- 检索耗时跟正文总量走：0.22 MiB → 0.10 s，3.83 MiB → 0.77 s（约 190 ms/MiB）。100 MiB 的库不敢想。
- `context` 每次返回所有页全文：120 页 × 32 KiB 时单个响应 2.8 MiB，每张工单都要付一次。

### 7.3 三种修法（需要你选一个方向）

1. **保持每次全量核对**：不改，简单、最安全，但全局知识库不可用（上表已说明）。
2. **按变化信号增量核对（推荐）**：常驻进程记住上次核对的（路径 → 内容哈希）快照，每个请求先用 stat 信号
   （大小、mtime、ctime、inode）和目录列举判断有没有变化；没变就复用，变了就全量重哈希。任何写入都会改 ctime，
   即使把 mtime 改回去也躲不过；`verify`/`rebuild` 永远做全量核对，外部编辑冲突的检测用变异测试固定
   （同大小换内容、恢复 mtime、增删文件、插入软链接各一条）。
3. **只读操作不核对**：最快，但会读到被外部篡改的内容，违背现有「失败即停」的原则，不建议。

配套（与第 2 条一起做）：检索产物按页内容哈希增量更新，查询时不再全量重算校验；`context` 支持按范围
（namespace / 邻域）取页面；lint 的两两比较改成候选剪枝，或把全量审计移到显式 `quality-audit`。
验收目标（实测后确认，不是承诺）：5000 页时每张工单 ≤ 0.5 s；2 万块 / 20 MiB 正文时 `retrieve` ≤ 50 ms；
导入 1000 个文件 ≤ 10 分钟。

### 7.4 已实现：增量核对（续七十一）

- 每个文件有一个变化信号：大小、mtime、ctime、inode、mode（`platform/fs.c: mc_signature`；末段永不跟随软链接）。
  原生会话跨请求共享一份内存里的核对备忘（`vault/verify.mbt`）：信号与目录哈希都命中才跳过读取；
  任一不符就整文件重读、重算哈希并重新做结构校验。备忘只在内存里，从不落盘，也不成为权威。
- 页面结构校验还依赖「它声明的每个链接都指向有效页面」，所以备忘为每页记下链接表，只有链接仍全部有效才复用；
  其余条目（状态记录等）自身结构自足，可以跨目录变更复用。
- 读取前后各取一次信号，两次不同则不记备忘（校验期间被改的文件不能被当成旧内容记住）。
- `verify` 与 `rebuild` 走 `verify_full`：忽略备忘、全量重读，作为显式审计。
- WASM 两端没有 stat：`stat` 返回 None，行为与改动前完全一致（全量读取）。
- 实测（本机，600 页 / 2400 个目录条目）：`fingerprints` 332 → 17 ms，`list-pages` 335 → 11 ms，
  `plan` 448 → 133 ms，`search` 523 → 240 ms；`verify` 保持 440 ms 全量审计；lint 仍为 3.7 s（未改，§9 待做）。
- 十条差分测试固定这些规则（`vault/verify_wbtest.mbt`）；端到端新增「同字节数改写并恢复 mtime」「替换为软链接」
  「删除页面」三种外部编辑，都在同一个常驻会话里验证，证明备忘不会掩盖外部改动。
